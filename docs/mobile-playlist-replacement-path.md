# 移动端歌单平替与普通播放路径差异（2026-10-19）

本次只修复 Android，PC 已正常的实现不改动。以下设备观察均来自实际安装的 v1.0.3/r47；源码修复未打包、上传或替换主应用。

## 同机证据

手机与 PC 均安装 r47，七份音乐源脚本的 SHA256 一一相同，但配置不等价：PC 第一位为“星海音乐源”、目录为 wy；手机第一位为“野花”、目录为 wy。PC 的“野花”在第二位、目录为 kw。手机开启 smoothPlayback，普通播放已能优先使用可用源。

手机 296 首“喜欢”歌单的 autoReplacement=true。第一首导入条目为《如果の事》，实际保存的三个候选分别为《如果的事》范玮琪／张韶涵、《如果的事 (R&B版)》陶宏杰、《如果的事》Superluckyqi；三者均绑定手机的“野花”。因此不能归因为没有搜索或没有同名结果。

在手机 r47 上重复执行生产 replacementSearch/replacementExact/replacementProbe：找到上述候选，“野花”三个解析均明确返回上游 Error，未到音频探测阶段。第一项本轮含初始化/等待耗时约 61.7 秒，后两项约 1.5 秒和 0.7 秒。该耗时是一次观察，不是代码新增的固定超时。

把相同的第一候选交给同一手机的普通生产 resolve，再做相同的音频探测：选择“星海音乐源”，取得 high 地址，音频前缀检查通过。这里只证明实际解析和音频检查，不宣称完成真机解码或整首试听。

各次辅助检查 personalUnchanged=true。未更改音源顺序、网络权限、歌单、喜欢或收藏；测试辅助包独立于主包。

## r47 为何失败

自动入口按歌名查找，第一搜索源有三项结果即停止收集。原 replacementExact 将候选绑定到产生结果的单个源，只选一档音质；失败即消耗该候选。这与单独搜索后普通播放可切换音源／音质的 resolve 不同。

所以三个候选都出自同一失效源时，会先后三次很快失败，随后跳过原导入歌曲。PC 排在首位的源可用，因此同一缺陷没有在其当前配置下暴露。七个脚本相同不等于源顺序、搜索目录和播放策略相同；不据此声称任何一个源在所有设备永久失效。

## 本地修复后的完整路径

1. 仅有歌单上下文、且该歌单自动平替开关开启时进入自动流程。原曲、喜欢、收藏、歌单顺序继续保存。
2. 播放服务先检查能与当前原曲／替代关系对应的缓存；可复用则走缓存。已有替代关系时重新取得其连接，按实际播放回调确认 verified。
3. 没有可用关系时，用原导入歌名搜索。依启用的搜索音源收集有效结果，前三个去重候选构成该轮候选池；不要求原曲与候选的歌手、时长一致，不额外引入第四首。可能选中翻唱或混音。
4. 保存第一个候选的额度后，把该候选交给普通播放 resolve。沿用现有源顺序／流畅优先、显式来源选择与音质配置，在同一目录可直接复用身份；跨目录继续使用普通播放的同录音匹配，不能把不匹配元数据误当成候选。
5. 当前源／音质有明确错误时，依普通播放计划继续下一档或下一源。原普通解析器对可重试的瞬时传输错误最多重试一次；同一候选本轮使用已尝试集合，避免重复无界调用。一个候选可有多次网络调用，候选额度仍为一次。
6. 取得地址后检查真实音频响应。HTTP 错误、非音频内容等明确失败时，继续当前候选尚未尝试的源／音质；全部用尽才进入第二个候选，最多第三个。
7. 音频响应通过仅保存 pending。交由播放器开始实际播放，播放回调确认 verified；取得地址或下载少量字节不等于已经播放。
8. 候选全部明确失败才跳过歌曲。若搜索接口本身全失败或没有可用搜索源，停止并提示搜索失败，不伪装为“这首没有歌曲”后快速扫过整个歌单。成功搜索但确实没有有效候选，仍作为候选不可用处理。
9. 不设累计解析时限；等待中的请求不会因总耗时换歌。暂停、换歌或取消会取消底层工作，并在保存前校验取消状态；保留已用候选额度，迟到结果不能绑定回原选择。完整结束的失败轮，下一次新播放可重新搜索；第三次等待中取消不释放额度。

三次上限指 **三个候选歌曲**，不再错误地把某个源一次解析失败等同于整首候选不可播放。PC 现有路径不在本次改动内。
