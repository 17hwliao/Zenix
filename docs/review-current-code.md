## 当前版本如何接收后续版本

更新路径固定为：当前客户端读取原固定通道 → 验证原 RSA 公钥及 schemaVersion 1 → 判断该平台递增构建 → 下载新的不可变地址并逐跳检查 HTTPS → 验证大小与 SHA256 → 系统覆盖安装且保留原数据目录 → 新客户端继续读取同一通道与公钥。

1. 原 `config/distribution.json` 中 main 的 stable / preview 地址、公钥与清单封装保持兼容。不能因为改公开版本而迁移旧客户端唯一知道的入口，也不能要求客户端先升级到某个中间版才读新格式。
2. Android 保留 `com.zenix.musicplayer` 与证书 SHA256 `b40080130e2186eba857ea2778350b88fe896c33cc9e0116493022e5adb8514a`。清单 build 与实际 versionCode 相等，且大于已安装构建。Windows 的实际 package.json `zenixBuild` 与清单相等，公开版本不回退。公开版本可继续为 1.0.0，也可在获准后增加；内部构建始终递增。
3. r34 曾公开，删除不能释放身份。下一份新字节使用 **r35 或更高**，并大于随后所有已发行构建；不能以“原版”名义重置为 1。同一工件身份的版本、下载 URL、大小、SHA256 与其他字段都不能替换。
4. 新安装器使用新文件名和独立 URL；旧正式包与缓存清单可能仍引用的地址继续保留。2026-10-10 获准删除历史包是一次例外，原链接已失效，需要重新检查更新；不能把这项例外用于未来清理。
5. 只改一端时，另一端在新签名清单中继续提供已签名的原工件。`--retain-windows` / `--retain-android` 仅允许保留当前 stable 工件的完全相同内容，并再次核验实际包。preview 超前时，未改动的 stable 平台可以保持原包；不能借保留参数签入其他旧包或把改动平台回退。
6. 发布次序为先上传新的不可变工件，核对远端大小与 SHA256，再切换 main 签名清单。普通开发 / 构建不会自动执行发布。本轮工作流新增的是校验依赖与门禁，没有新增自动发布触发器。正式发布仍需实际覆盖安装、数据保留和安装后后续更新证据。

| 路径 | 本轮证据 | 本轮未证明的部分 |
| --- | --- | --- |
