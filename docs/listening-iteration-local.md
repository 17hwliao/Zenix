## 关闭窗口与 Android 媒体通知

- Windows 关闭主窗口后隐藏到系统托盘，保留播放器和音源任务。点击托盘恢复；菜单提供播放 / 暂停、上一首、下一首及明确的完全退出。系统退出和更新安装器调用的 `app.quit()` 继续走真实退出，不被隐藏逻辑截住。系统托盘不可用时保留原窗口退出路径。
- Android 在解析前向 MediaSession 提供当前歌曲身份；加载期间使用带 MediaSession token 的通知，展示标题、歌手、当前阶段与上一首 / 暂停 / 下一首控制。就绪后优先交回 Media3 媒体通知，避免普通加载通知覆盖实际播放状态。音频解码仍由原生服务负责。

本轮没有复制 AlgerMusicPlayer 的组件源码；参考其功能组织与交互思路，使用 Zenix 现有 React / Electron / Android 播放架构实现。

## 2026-10-17 首次代码 Review（修复前记录）

本轮审查覆盖已批准功能迭代、歌单链接迁移、设置调整与 Android 补齐的本地改动及相关调用方。更早的 r40 源兼容改动不重新算作本阶段成果。复用前述编译与自动检查，仅对具体疑点作最小验证；没有操作手机、执行安装或发布。本次只审查，以下问题尚未修复，当前源码不能据既有通过日志直接进入打包交付。

1. **P1 / Android 播放阻断**：`PlaybackService.select` 为提前展示通知，调用 `player.setMediaItem` 时构造了没有 URI 的 `MediaItem`。实际依赖 Media3 1.11.1 的 `ExoPlayerImpl.setMediaItems → createMediaSources → DefaultMediaSourceFactory.createMediaSource` 会同步检查非空 `localConfiguration`；没有 URI 时该字段为空，因此在本地歌曲 `start` 或网络 `resolveNext` 前抛异常。已从本机实际 AAR 的字节码确认调用与检查，没有将静态验证写成手机复现。解析期通知应独立使用歌曲元数据，取得有效音频地址后再向 ExoPlayer 设置媒体源。原有 JVM 用例编译的是源调度及队列等模块，React 用例替代原生桥；两者没有执行这条真实 Service/ExoPlayer 初始化链，编译通过也不会捕捉这个运行时错误。
2. **P2 / PC 空队列“下一首播放”退化**：`PlayerController.playNext` 改为仅委托 `editQueue`，丢失原来在没有当前歌曲时调用 `playTrack` 的路径。实际生产控制器的隔离最小复现：HEAD 添加后选中并播放；当前源码只得到一首队列、`track` 为空且 `playing=false`。应保留空队列首次选择与起播行为。
3. **P2 / PC 已存在的大队列无法整理**：`setQueue` 和歌单“播放全部”允许超过 1000 首，新的 `editQueue` 却对所有操作结果统一拒绝超过 1000 首。实际生产控制器最小复现可载入 1500 首，但移动一首、仅删除一首均抛“队列超过上限或包含重复歌曲”；`restore` 同样不能恢复超过 1000 首的旧队列。应统一创建/编辑的容量契约，并允许既有大队列重排、缩减及有效撤销。

首选下一步是修复 Android 播放阻断，再补真实媒体项初始化和空/大队列边界的最小回归（预计中等成本）。这是本次证据支持的改进方向，未由 Review 自动扩展为实施、实机验收或发行授权。
